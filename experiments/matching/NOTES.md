# 対戦の組み方による収束の比較（未提出の実験記録）

2026-11-27に実施した探索の記録です。PRは作成していません。`matching_probe.cpp` は試作で、テストはまだありません。対戦の組み方を変えると対戦履歴そのものが変わるため、同じ履歴で推定方法を比べる実験とは別の実験です（AGENTSの公平な比較の8）。

## 結論

- 推定レートで実力の近い相手を組ませ、全履歴推定で推定すると、評価用10試行のMSEの平均が「ランダム対戦＋今のGlicko-2」より22.0%下がった。10試行すべてで改善した（−17.2〜−24.5%）。
- ランダム対戦の200試合時点のMSEに150試合で達した（25%少ない対戦数）。100試合時点のMSEには80試合で達した。
- 効果には推定方法と組み方の両方が必要だった。今のGlicko-2のままでは組み方を変えても改善せず（−1.1%）、推定レートの順に厳密に並べると18.4%悪化した。

## 方法

各ラウンドで全員が1試合ずつ行う（ランダム対戦と同じく、各人の対戦数は揃う）。組み方は推定レートだけから決め、潜在能力は使わない。勝敗は生成モデルの真の勝率から引く。

| 組み方 | 内容 |
| --- | --- |
| random | 全員を無作為に並べ、隣どうしを組ませる |
| sorted | 推定レートの順に並べ、隣どうしを組ませる（同点は無作為） |
| sampled | 推定レートに λ × RD × 標準正規乱数を加えた値で並べ、隣どうしを組ませる |

組み方に使う推定は、毎ラウンド全履歴推定（事前分布のRD 210）で更新した。できた履歴に対して、全履歴推定（RD 210）と今のGlicko-2（RD 350・σ 0.06・τ 0.5、期間10試合）の予測を共通の `MseEvaluator` で評価した。1,000人・各200試合・評価間隔10試合・標準正規分布の能力・`probit_1d`・`performance_std = 1`。

調整用の5試行（シード2026112511〜53）でλを選び、評価用の10試行（2026113011〜2026113103）で確認した。評価する組み方（random、sampled λ = 0.5、sorted）は評価用の試行を実行する前に決めた。randomはこの試作の乱数の使い方で作った履歴で、既存の生成（`generateMatches`）とは乱数の消費順が異なる。

## 注意

- 組み方を変えると対戦履歴が変わる。同じ履歴で推定方法を比べる主実験とは別の結果として扱う。チームメイトのスキルマッチ（PR #41）と目的が重なるため、組み方の採用は調整が必要。
- 今のGlicko-2は、レートの近い相手が続くと10試合ごとの期間更新で古いレートを使い続けるためか、sortedで悪化した（原因は未確認）。組み方を変える場合は推定方法も一緒に検討する必要がある。
- 能力が変化しないことを前提にしている。毎ラウンド全履歴推定をやり直すため、1,000人・200ラウンドで1試行約30〜40秒かかる（Apple M4、1スレッド）。
- ランダム対戦での1試合の情報量は、真の勝率が一様分布になるため平均 E(1−E) = 1/6 で、互角の対戦の1/4より小さい。実力の近い相手を組ませる効果はこの差で説明できると考えられる（仮説）。

## 再現

```sh
cmake -S . -B build/release -G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build build/release
c++ -std=c++17 -O3 -Iinclude experiments/matching/matching_probe.cpp build/release/libproject10_core.a -o build/release/matching_probe
./build/release/matching_probe random 210 evaluation
./build/release/matching_probe sampled 210 evaluation 0.5
./build/release/matching_probe sorted 210 evaluation
```

環境：macOS 26.6.2、Apple M4、Apple clang 17.0.0、CMake 4.4.4、Ninja 1.13.2。
