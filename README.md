# Project10 — 競技における様々な条件下での適切なレーティング

プロジェクト実験2026・第10班のリポジトリです。仮想的な対戦データを使い、レーティング手法が対戦勝率をどれだけ正確に推定できるか、対戦数とともに誤差がどう変化するかを比較します。

現在は、設定ファイルの読み込み、プレイヤーID・正規分布に従う潜在能力の生成、プロビットモデルによる真の勝率の計算、ラウンドごとの対戦組み合わせ・勝敗生成とCSV出力まで実装しています。C++17・CMakeでビルドし、CTestで小規模な動作確認ができます。Elo・Glicko・Glicko-2・TrueSkill、推定レートからの予測勝率、MSE集計、グラフ生成は未実装です。以下の比較実験の説明には計画を含み、比較結果を示すものではありません。

初期実験では、生成モデルで仮定した能力から対戦勝率と勝敗履歴を作り、同じ履歴を各手法に与えて比較する方針です。「仮定した能力」「生成モデル上の真の勝率」「推定レート」「予測勝率」を区別します。真の勝率とは仮想モデル内の正解値であり、現実の人間の実力を測定した値ではありません。[第7回会議](https://app.notion.com/p/3f9751d0ef6d80638dc5defdc6a09deb)

授業の目的は、チームで動くシステムを完成させ、設計・実装・検証を通して学んだことを説明することです。見た目や周辺機能よりも、比較実験の中核と評価・考察を優先します。生成したゲームの性質が評価結果に影響するため、特定のモデルでの優劣をすべての競技へ一般化しません。[チーム開発ハブ](https://app.notion.com/p/3d8751d0ef6d81c6944ad100e7eb5e69)、第6回会議の教員コメントを参照してください。

## 初期実験の方法（一部実装済み）

以下は[第7回会議（2026-10-16）](https://app.notion.com/p/3f9751d0ef6d80638dc5defdc6a09deb)の「決定値・保留理由」欄と末尾の「決定事項」に基づきます。同じページには会議前の未決定表記や説明用サンプルも残っているため、細部が曖昧なものは後述の確認事項として扱います。

| 項目 | 議事録上の初期条件 |
| --- | --- |
| 対戦形式 | 1対1、引き分けなし、実験中の能力は固定 |
| 能力 | 1次元、標準正規分布から生成 |
| 試合ごとの変動 | 全員共通のパフォーマンス標準偏差 `σ_g = 1` |
| 勝率生成 | 共通の変動幅を持つ1次元プロビットモデル |
| 人数 | 1,000人。動作確認は少人数で行う |
| 対戦数 | 1人当たり200試合 |
| 対戦相手 | ランダムに選択し、全手法へ同じ対戦履歴を渡す。具体的な組み方は要確認 |
| 評価間隔 | 各人10試合ごとに集計 |
| 主指標 | 生成モデルの勝率と予測勝率の平均二乗誤差（MSE）、試合数に対する誤差の推移 |
| 乱数の管理 | 能力、対戦組み合わせ、勝敗生成を分けて管理。シード値と試行数は未確定 |

勝率生成式は次のとおりです。`θ_i` はプレイヤー `i` の仮定した能力、`Φ` は標準正規分布の累積分布関数です。`σ_g` は試合ごとの変動であり、各レーティング手法が持つ推定の不確実性とは別です。

$$
p_{ij}=\Phi\left(\frac{\theta_i-\theta_j}{\sqrt{2}\sigma_g}\right)
$$

処理は次の順序で構成する計画です。現在は手順1のプレイヤーID・潜在能力・正解の勝率・対戦履歴の生成まで実装しています。手順2以降の処理は未実装です。

1. 仮想プレイヤーと正解の勝率を生成し、共通の対戦履歴を作る。
2. 各手法にプレイヤーIDと観測済みの対戦履歴を渡す。潜在能力と正解の勝率は渡さない。
3. 各手法が共通の評価時点・プレイヤーペアに対する予測勝率を個別のCSVへ出力する。
4. 共通の評価処理で、各手法の予測と正解の勝率を照合してMSEを計算する。
5. 手法ごとのMSEをCSVへ出力し、対戦数に対する誤差の推移をグラフにする。

評価対象のペア集合を `S` とすると、MSEは `Σ(予測勝率 − 正解勝率)² / |S|` です。議事録の形式例では自己対戦を除き `i < j` のペアを扱います。1,000人では499,500組です。レートそのものの尺度や、集団のレート分布が正規分布に近いかだけで手法の優劣を判定しません。

### チームで最終確認すること

- **対戦数と対戦順**：各人200試合・全100,000試合を揃えるため、下記のシャッフルによるラウンド方式を実装しました。議事録の「ランダムに選択」を具体化する実装案であり、短い最終期間の扱いとともにチームの最終確認が必要です。
- **更新期間**：決定表には「毎試合（Glicko以外）／10試合1期間（Glicko）」、設定例の説明には「Glicko・Glicko-2は各人10試合の期間」とあり、Glicko-2の扱いに曖昧さがあります。期間の意味と更新順を統合前に確認します。評価間隔と更新間隔は区別します。
- **再現条件**：能力・対戦組み合わせ・勝敗はそれぞれ独立した `std::mt19937_64` を使用します。潜在能力は `std::normal_distribution<double>`、ペア分けは `std::shuffle()`、勝敗は `std::bernoulli_distribution` で生成します。正式なシード値、複数試行の本数、各手法の初期値・パラメータ・予測式は別途確定します。議事録のシード・予測値・MSEの例は実験結果として使いません。
- **入出力契約**：現在の設定と実装済みCSVは後述の仕様を使用します。未実装のCSV・更新期間等は議事録を確認してから追加します。1試行につき1つの設定を用意する運用を維持します。
- **追加評価**：実行時間・メモリ測定は副次的な評価候補です。IS計算サーバーの利用条件やCPU固定は未確認です。

## 環境構築・実行方法

議事録末尾の決定事項では、**実装言語はC++に統一し、グラフ生成のみPythonを認める**方針です。開発基盤はC++17・CMakeを使用します。C++17の `std::filesystem` が利用できるコンパイラと標準ライブラリ、CMake 3.20以上、ビルドツールが必要です。Ninjaを使う場合はNinjaを、Visual Studioを使う場合はC++ビルドツールを用意してください。現在のビルドとテストにPythonは不要です。

JSONは同梱のnlohmann/json 3.12.0のみを使用します。CMake構成時のネットワーク取得は行いません。依存の管理方針は[third_party/README.md](third_party/README.md)を参照してください。

リポジトリの取得にはGitとGitHub上のアクセス権が必要です。新しく取得する場合は、配置したい親ディレクトリで次を実行します。

```sh
git clone https://github.com/Project-Programming-2026/Project10.git
cd Project10
```

すでに取得済みの場合は、そのリポジトリのルートで作業してください。

### ビルド

NinjaとC++17コンパイラがPATHにある環境では、Windows・Linuxとも次の手順でビルドします。

```sh
cmake -S . -B build/dev -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/dev
ctest --test-dir build/dev --output-on-failure
```

WindowsでVisual Studioのジェネレーターを使う場合は、別のビルドディレクトリを指定します。

```sh
cmake -S . -B build/vs
cmake --build build/vs --config Debug
ctest --test-dir build/vs -C Debug --output-on-failure
```

WindowsではGCC 16.2.0（MSYS2 UCRT64）・CMake 4.4.4・Ninja 1.13.2でビルドとCTestを確認しています。Linuxでは2026-10-19にWSL2 Ubuntu 24.04.5 LTS・GCC 13.3.0・CMake 3.28.3・Ninja 1.11.1で、DebugビルドとCTest全14件の成功を確認しました。Linuxのリンク保護テストもスキップせず成功しています。Visual Studio手順は未検証です。

`project10_core` に設定と生成処理、`project10` に `main.cpp` をまとめ、全 `.cpp` を明示的に登録しています。テスト不要の構成は `-DBUILD_TESTING=OFF` で作成できます。

### 対戦生成方式（実装案）

`uniform_random` は、全プレイヤーIDを各ラウンドで `std::shuffle()` し、隣接する2人を順に対戦させる方式として実装しました。各人は1ラウンドに必ず1試合を行い、全 `matches_per_player` ラウンドを実行します。自己対戦はなく、別ラウンドでの同一ペアの再戦は許可します。人数は2以上の偶数に限定し、奇数人数の休み番は実装していません。

これは第7回会議の「ランダムに選択」を、各人の対戦数が揃う形へ具体化した実装案です。無制約に毎試合2人を独立抽選する方式とは対戦履歴の分布が異なるため、正式な比較への採用はチームで最終確認してください。

ペア分け用の `std::mt19937_64` は `seeds.matching`、勝敗用は `seeds.result` で実行開始時に一度だけ初期化します。各対戦のA側の真の勝率を既存の `calculateWinProbability()` で計算し、`std::bernoulli_distribution` から勝敗を生成します。`ground_truth.csv` の再読み込みは行いません。能力は `seeds.ability` で別に生成し、勝敗や能力の乱数消費がペア分けを変えないようにします。

### 出力と上書き確認

成功時は次の5ファイル（設定と4つのCSV）を出力します。既存の `runs/run_XXXX/` がある場合は、空でも `Overwrite config.json and the 4 generated CSV files? [y/N]:` と確認します。`y` または `Y` を入力した場合だけ、この5ファイルを現在の設定で上書きします。空欄・`n`・その他の入力・入力終了では、既存ファイルを変更せず終了コード1で中止します。フォルダー全体や無関係なファイルは削除しません。

上書きは開発中の動作確認用です。正式な比較実験の結果は、新しいrun IDで保存してください。同じシードでも人数・分布・`performance_std`・コード・実行環境が変われば結果が変わる可能性があります。

書き込み前に5つの出力先をすべて検査し、シンボリックリンク（リンク先が存在しない場合を含む）、複数のハードリンクを持つファイル、通常ファイル以外の既存エントリがあれば、どの出力ファイルも更新せずに停止します。

同じrunへの同時書き込みは `runs/.run_XXXX.lock/` の排他的作成で防ぎます。新規生成・上書きのどちらも、確認から設定保存までロックを保持し、使用中のrunは拒否します。正常終了・中止・例外時には解除しますが、強制終了などでロックが残ることがあります。その場合は同じrunを使用するプロセスがないことを確認し、残存結果を確認・保管してから、その空のロックディレクトリだけを手動で取り除いてください。

```text
runs/run_XXXX/
├── config.json             読み込んだ設定のスナップショット
├── players.csv             列：player_id
├── latent_parameters.csv   列：player_id,theta_0
├── ground_truth.csv        列：player_a,player_b,p_a_wins
└── matches.csv             列：match_id,period_id,player_a,player_b,result_a
```

`ground_truth.csv` は自己対戦を除く `i < j` の各ペアについて、`player_a` が勝つ確率を保存します。逆方向は `1 - p_a_wins` で復元できます。人数を `N` とするとデータ行数は `N(N-1)/2` で、8人では28行、1,000人では499,500行（いずれもヘッダーを除く）です。浮動小数点数は `max_digits10` の精度で出力します。計算には `std::erfc()` を用い、能力は有限値、パフォーマンス標準偏差は正の有限値に限定します。勝率の計算に追加の乱数は使いません。

JSONの未使用項目もスナップショットに残します。潜在能力と真の勝率は生成・評価・検証専用であり、将来のレーティング手法へ渡しません。書き込み失敗時には一部のファイルだけが作成・更新される場合があります。同じrun IDで再実行すると再び上書きを確認します。失敗した試行の結果も担当者が確認・保管し、正式な比較実験は別のrun IDで記録してください。

同じシード・設定・実行環境では生成結果を再現します。標準ライブラリが異なると正規分布の乱数列は一致するとは限らないため、比較する手法には生成済みの共通データを渡し、コンパイラ・標準ライブラリ・設定・入力のハッシュを記録します。

`matches.csv` の仕様は次のとおりです。

| 列 | 意味 |
| --- | --- |
| `match_id` | 0始まりの連番。CSVの行順が試合順 |
| `period_id` | 0始まり。`ラウンド番号 / rating_period_matches_per_player` の整数除算 |
| `player_a`・`player_b` | シャッフル後の隣接するプレイヤーID。A・Bの並びを保持 |
| `result_a` | Aが勝てば1、負ければ0。引き分けなし |

試合総数は `num_players * matches_per_player / 2` です。初期条件では1,000人・200ラウンドで100,000試合、10ラウンド1期間で `period_id` は0〜19です。末尾の端数ラウンドは切り捨てず短い最終期間へ含めます。例えば5ラウンド・2ラウンド1期間なら2＋2＋1ラウンドの3期間、期間ラウンド数が総ラウンド数より大きければ全体で1つの短い期間です。この端数の扱いも実装案としてチームで確認してください。Glicko・Glicko-2の更新処理を決定・実装したことは意味しません。

`samples/run_0000/` に含まれるのは、プレイヤーID・潜在能力のCSV、使用した設定とチェックサムです。対戦履歴を含む共通入力は `samples/run_0001/` にあり、同じ `players.csv`・`matches.csv` と行順を利用します。`ground_truth.csv` は生成器の出力に含まれますが、どちらの共有サンプルにも含まれません。サンプルの更新は別途来歴・ハッシュとともに管理します。レーティング手法へ渡すのは、プレイヤーIDと観測した対戦履歴です。潜在能力と真の勝率は生成・評価・検証専用です。レーティングの実行自体は未実装です。

各自の実行結果は `runs/` へ保存し、共有入力のコピーを上書きしません。正式な比較では、使用する共通データを設定・ハッシュとともに固定します。Gitで扱える大きさならデータも管理し、大きい場合はチームの共有ストレージ等へ置いて、取得先・版・ハッシュをリポジトリに記録します。

### テスト

CTestは単体確認と13種類のCLI結合確認を実行します。JSON設定の読み込み、重複キーや不正なID・設定の拒否、CSVヘッダー・人数・IDの一意性、潜在能力の有限性、同一シードの再現性、出力先を検証します。上書きは拒否・空欄・入力終了で既存ファイルを保護し、`y`・`Y` で変更した設定が反映され、無関係なファイルが残ることを確認します。勝率計算は等能力で0.5、能力差1・標準偏差1で約0.76025、勝敗方向の反転、確率の範囲、不正入力、極端な有限値を確認します。`ground_truth.csv` は8人でヘッダーを含む29行、全28ペアの重複・欠落がないことを確認し、再現性・上書き確認の照合対象にも含めます。対戦生成は8人・5ラウンド・2ラウンド1期間で、各人の対戦数、各ラウンドの重複・欠落、自己対戦、連続ID、期間境界と端数、勝敗の0/1を確認します。シードごとの役割と再現性も検証します。加えて依頼された初期条件の1,000人・200ラウンドを単体とCLIで実行し、100,000試合・20期間を確認します。

未対応モデルの拒否、全出力先の事前検査、使用中runの拒否とロック解除も検証します。ハードリンクのテストでは、5つの出力先それぞれをrun外のファイルへのハードリンクに置き換え、上書きを承認しても共有するデータと他の出力が変わらないことをハッシュで確認します。シンボリックリンクの参照先の保全は専用テストで確認しますが、Windowsでリンク作成権限がない場合はそのテストだけをスキップとして明示します。スキップはリンク保全を検証済みという意味ではありません。

テストごとに `build/dev/test-work/` 以下へ専用ディレクトリを作成し、その中の `configs/` と `runs/` を使用します。リポジトリ直下の設定・結果は変更しません。テスト出力は調査用に残り、Git管理対象から除外されます。

| 責務 | 今後追加する際の配置規則 |

この表の未実装領域のディレクトリは、実際のファイル追加時に作成します。各担当は小さな処理単位で実装し、共通利用する操作のみをヘッダーで公開します。`players.cpp`、`latent_parameters.cpp` は生成処理を担当し、`generatePlayers(int)` はIDの配列、`generateLatentParameters(...)` は潜在能力の配列を返します。`probit.cpp` の `calculateWinProbability(...)` は2人の潜在能力とパフォーマンス標準偏差から真の勝率を返します。`matches.cpp` の `generateMatches(...)` は対戦履歴の配列を返し、潜在能力・正解勝率は履歴に含めません。CSV出力は `io/csv.hpp` の `writePlayers`・`writeLatentParameters`・`writeGroundTruth`・`writeMatches` が担当し、`main.cpp` で接続します。

レーティング本体へ正解情報が混入しない境界を維持し、各手法の出力は共通の評価処理へ渡します。提案手法は `ratings`、マッチングの変更は `simulation` に追加し、比較対象・対戦履歴への影響を記録します。

追加する `.cpp` は `CMakeLists.txt` の適切なターゲットへ明示的に登録し、実行の統括は `main.cpp` に置きます。`.editorconfig` に従い、C++は半角スペース2文字でインデントします。既存コードの命名は目的と無関係に変更しません。

ビルド生成物は `build/` などのビルド領域へまとめます。外部ライブラリのファイルを誤って除外しないよう、拡張子によるC++生成物の一律除外は行いません。ルートの既知の実行ファイルのみ個別に除外しています。

ソース・ヘッダー・設定・共有サンプル・テスト・ビルド設定・文書・同梱依存はGit管理対象です。`runs/`、ビルド領域、ルートにある既知の実行ファイル、IDEのローカル設定、Pythonキャッシュは `.gitignore` で除外します。CSV全体を除外する規則は設けず、共有CSVは `samples/` で管理します。すでに追跡されているファイルには `.gitignore` は遡及しないため、作業前から存在する削除・移動差分は別途確認してください。

### PRタイトルの書き方

PRのタイトルとコミットメッセージは `type(scope): 日本語の説明` の形式で書きます。

- **`type`（必須）**：変更の種類です。「機能追加か、不具合修正か、文書の更新か」を表します。下表から選びます。
- **`scope`（任意）**：変更対象の機能・領域です。例えば `elo`、`glicko2`、`simulation`（データ生成）、`evaluation`（評価処理）など、対象が分かる短い名前を使います。担当者名やブランチ名ではありません。適切な範囲を絞れない場合は、括弧ごと省略します。
- **説明（必須）**：何を追加・修正するかを日本語で簡潔に書きます。コロンの後ろには半角スペースを入れます。

| type | 意味・使う場面 |
| --- | --- |
| `feat` | 新しい機能を追加する |
| `fix` | 不具合や誤った動作を修正する |
| `docs` | READMEなどの文書を追加・更新する |
| `style` | 空白・整形など、動作を変えない表記を修正する |
| `refactor` | 機能や動作を変えずにコードの構造を整理する |
| `perf` | 計算時間・メモリ使用量などの性能を改善する |
| `test` | テストを追加・修正する |
| `build` | ビルド設定や依存関係を変更する |
| `ci` | CIの設定や自動検査を変更する |
| `chore` | 上記に当てはまらない保守作業を行う |
| `revert` | 過去の変更を取り消す |

例えば `feat(elo): 対戦結果によるレート更新を追加` は、種類が「機能追加」、対象が「Elo」です。`docs: 初期実験の条件を明記` は、対象の括弧を省略した文書更新です。研究条件や推定結果が変わる変更を、動作不変を意味する `style` や `refactor` として扱わないでください。

### PR本文のテンプレート

PR本文は[テンプレート](.github/PULL_REQUEST_TEMPLATE.md)に沿って、概要・背景・変更内容・検証・研究条件への影響・チェック項目・未解決事項を記入します。関連するIssueやタスクも添え、該当しない欄には「なし」または理由を書いてください。コマンドや実験条件を記載するだけでなく、実際の確認結果を示します。
